Secure Builder · engine walkthrough · for the whole team

How the engine actually works

Secure Builder is not an app — it's a factory that builds apps. Its real product is the paper trail proving each app was built safely enough to be allowed onto a military network. This is the whole workflow, end to end, written for someone who doesn't write code.

01

The problem it exists to solve

When a team builds software for a Department of Defense network, they can't just ship it. A separate platform team inspects it first and decides whether it's allowed to run — that permission is called an ATO, Authority to Operate. That inspection is the bottleneck: it finds dozens of problems, the dev team fixes them, resubmits, waits again. Months.

Secure Builder's bet: do the inspection during the build, not after. If every feature is checked against the same rules the platform team will use, the app arrives at intake nearly clean, with the evidence already attached. The bottleneck shrinks.

Say this out loud, every time

Secure Builder does not grant that permission. It's a pre-flight check, not the flight clearance. The platform team remains the only approval authority. Overstating this is the one failure mode that turns the engine from an asset into a liability.

02

How to read the rest of this page

Every check in the engine falls into one of three classes. The difference between them is the most important thing on this page — the engine is deliberately blunt about which of its own gates are real automation and which rest on a person paying attention.

Machine Provable from the record — exit codes, coverage numbers, commit order. Can't be talked out of.
Attested A person says it happened. Genuinely useful, not verifiable. Never call it "verified."
Hard stop Work cannot advance without a human typing something specific.
03

The cast — eleven specialists, one job each

Instead of one AI doing everything (and quietly making decisions outside its competence), the engine uses eleven named roles. Each has a single responsibility and a specific list of files it is permitted to touch.

RoleJob, in plain terms
AtlasOnboarding lead. Works out what the project even is, before anyone builds anything
CharterProduct manager. Writes what the product should do
ScribeStory analyst. Hunts gaps and contradictions in the work descriptions
MarshalScrum master. Hands out the work, one piece at a time
KeystoneArchitect. Structural decisions — database shape, how systems talk to each other
PrismUX designer. Screens, interactions, accessibility
ForgeDeveloper. Writes the actual code
CrucibleTest architect. The quality inspector
SentinelSecurity gatekeeper. The security inspector
BastionDevSecOps. Deployment plumbing and hardening
CodexTech writer. Documentation
The rule that makes this matter

No role acts outside its lane. If the developer starts making architectural decisions, that is a recorded finding — not a shrug. This is a deliberate defense against what the industry calls excessive agency: an AI quietly expanding its own authority. The file-ownership half of this is mechanically checkable; the judgment half — a decision buried inside a file the role was allowed to edit — stays with the reviewer. The engine says so rather than claiming full automation.

04

Setup — answered once, permanent

Cloning the engine for a new project starts with a short decision tree. These are design-time constants, not switches you flip later. The answers decide which security checks turn on for the life of the project.

Track

A web app, or an Android app?

Security tier

IL4 (sensitive but unclassified) or IL6 (classified). Android is always IL6.

Provider

AWS, Azure, or tactical — a team-owned classified network with no cloud services at all.

Enforcement

Can a central server block a bad merge, or is this an offline machine where enforcement rests on local checks plus discipline?

Compute profile

Which local AI models fit the available hardware.

05

Loop A · Phase 0 — work out the project

Runs once, before any code exists. Nothing is built until a human has approved a written description of what's being built. Atlas runs six stages with a checkpoint between each.

  1. IntakeIf a codebase already exists, the engine reads it and drafts a "here's what exists today" document. A privacy filter strips real server names, account numbers and passwords before anything is written down — replaced with placeholders like <ACCOUNT_ID>. Every extracted fact is tagged with where it came from.
  2. Guided authoringThe engine interviews you and drafts the core set: what the product is for, how it will be structured, what security posture it must hold, and how to get from today to there.
  3. Gap check — a gateDoes any document contradict another? Is anything left unspecified? Loop until clean.
  4. BacklogBreak it into epics and individual work items — "stories" — each stamped with which piece of the intent it serves.
  5. Traceability check — a gateEvery story must trace to a stated goal, and every stated goal must have at least one story. No orphans in either direction.
  6. Cohesion criteriaWrite down in advance how you will later judge whether a finished epic actually delivered what it promised. This is what Loop C checks against.
Anti-bloat rule worth knowing

Beyond the core set, the engine may recommend at most three extra documents, targets two or fewer, and defaults to zero — and only where it can name the specific build failure that happens without that document. If it can't name the failure, it doesn't ask. The cap is a ceiling, never a quota.

Honesty stamp

Everything Phase 0 produces is an AI-assisted draft. It is not authoritative until a human ratifies it. An AI ratifying its own output is a protocol violation — the same violation as an AI approving its own code.

06

Loop B · One story, start to finish

This is the heart of the machine. Every single piece of work runs this exact sequence — no step skipped, no step reordered. The unusual part: it runs across two separate AI sessions that cannot see each other.

Session 1

Build

Starts cold, from a written brief. Ends without judging its own work.
  1. 01
    DispatchMarshal

    Marshal picks the next story and routes it to the right first specialist. A database change starts with Keystone. A screen starts with Prism. A plain feature starts with Forge.

  2. 02
    Write the failing test firstMachine

    Before any code is written, Forge writes the test that proves the feature works — and runs it. It must fail, because the feature doesn't exist yet. The failure output is pasted into the story file as evidence, and saved as its own timestamped checkpoint in the project history.

    Why this is backwards on purpose. A test written after the code tends to be shaped to pass it. A test proven to fail first, then passing, actually demonstrates something. And because these are two separate timestamped checkpoints, the order is verifiable later — it's a receipt, not a claim. If the failing-test checkpoint isn't there, the story fails automatically, no matter what the AI asserts.
  3. 03
    Write the codeMachine

    Second checkpoint. The tests now pass. Two checkpoints, in that order, or the story is dead on arrival at the next gate.

  4. 04
    Hand off blind

    The build session writes a self-contained brief for the inspection session, and then ends. It does not inspect its own work. Ever.

The bias firewall The inspection session sees only the story and the code changes — never the builder's reasoning, justifications, or self-assessment.
Session 2

Gates

A fresh session. No memory of how the work was argued for.
  1. 05
    Quality gateCrucibleMachine

    Pass or fail. No partial credit.

    • Were the two checkpoints made, in the right order?
    • Is enough of the new code covered by tests — 80% for core logic, 70% for request handlers — measured on this story's changes, not the project average, so a weak story can't hide behind a well-tested past
    • Negative tests. It is not enough to prove the feature works for an authorized user. Every endpoint must prove it rejects: someone not logged in, someone with the wrong role, someone reaching for another customer's data, and a malformed request
    • Does every acceptance criterion have a matching test, by name?
    • Do the linter, the type checker and the full test suite pass clean, with nothing skipped?
    • Do unreliable tests pass three times running?
  2. 06
    Security gateSentinelMachineAttested

    Also binary. Before judging anything, Sentinel must open and read each of its own checklist files and state out loud what it loaded. A gate run that skipped that is invalid and re-runs — forcing a real read pulls the instructions into working memory instead of trusting the model to recall them.

    Then the baseline: no passwords in the code, authentication runs before every request handler, roles enforced, database queries that can't be hijacked, error messages that don't leak internals, approved dependencies only. Stricter checks switch on for IL6 and Android projects.

    Every check cites a real control. Not a paraphrase — the actual government standards (NIST SP 800-53, DISA STIGs) are copied into the repository itself, so a citation points at a paragraph a person can open. That matters doubly on an offline network. Where a source hasn't been copied in yet, the manifest says so and the engine refuses to fake it from memory.
  3. ↺
    The self-healing loop — and its limit

    A FAIL sends specific findings back to the builder, who fixes and resubmits. But the loop is capped at three rounds. After the third it stops and escalates to a person.

    Why cap it. Two AIs auto-fixing to each other's checklists will eventually optimize for passing the checklist rather than for being correct. The cap is there because the failure mode is predictable.
  4. 07
    Manual security reviewHard stop

    The gate the whole design leans on, because it targets exactly what automated checks cannot catch. A person sits down and answers, in their own words:

    • Can a user reach data outside their role through an unexpected sequence of otherwise-legal actions?
    • Can an acceptance criterion be satisfied in a way that violates a stated "SHALL NOT"?
    • Does a chain of individually valid steps produce an unauthorized end state?
    • Is every data lookup scoped to who owns it, before anything is returned?
    • Can any combination of endpoints escalate someone's privileges?
    Anti-rubber-stamp rules. The prompt names the actual endpoints from this change, never a generic checklist. For security-sensitive work the reviewer must name each endpoint touched and state who can call it and what stops everyone else. A bare "looks good" is rejected. And the recorded approval says what was actually reviewed — so the audit trail never claims more diligence than occurred.
  5. 08
    Human approvalHard stop

    An explicit, typed "approved." Nothing else unlocks the next step — not a high test score, not a clean security scan, not an AI's confident assertion that everything is fine.

  6. 09
    PromotionRecorded

    Only now does the work become official. Three things happen, in order:

    • Sentinel appends rows to the gate log — the permanent evidence record
    • The work is merged
    • Marshal writes the brief for the next story, fully self-contained, because the next session begins with no memory of this one
    The gate log is append-only. Nothing is ever edited or deleted. Corrections are new entries. A security finding that's later fixed gets an additional row, not a rewrite. The project history itself is the tamper detector.
07

Loop C · Closing an epic

Individual stories can each pass and the assembled result can still drift away from the original intent. So when an epic completes, Atlas runs the cohesion gate against the criteria written back in Phase 0: does the finished whole still satisfy what it was for? Did any story hit its target in a way that violated a "SHALL NOT"? Is everything promised actually shipped?

The verdict is COHERENT or DRIFT. Drift blocks the epic from closing and sends it back to re-scoping.

08

What's automated, and what isn't

The engine's constitution has a dedicated section for this, and it is unusually blunt. Summarized:

CheckClassHow it's established
Test-before-code orderMachineVisible in the project history — the order can't be faked after the fact
Coverage, linting, types, no skipped testsMachineExit codes and numbers
Flaky testsMachineThree consecutive clean runs
Acceptance criteria → testsPartialName matching gets most of the way; judgment finishes it
Control citationsPartialThe citation is grounded in real source text; whether the mapping is right is human-confirmed
"Did the agent read its required documents?"AttestedNot verifiable. Caught only by its consequences — output that contradicts a document it was supposed to have read
Manual security reviewAttestedNot verifiable, by design. A person, or nothing
Why the wording matters

Those last two are called out repeatedly with an instruction never to describe them as "verified." The reason is simple: a plausible-but-wrong compliance claim is worse than no claim, because it gets believed.

09

The honesty clause — the part that protects us

There is a whole section of the constitution whose only job is to stop the engine being oversold. In plain terms:

This is not an ATO

It authorizes nothing. The platform team for each target network is the sole approval authority.

Not separation of duties

In a normal session the person who built it is the person who approves it. One human checking their own team's work. The two-session split makes the AI review more independent — it does not make it separation of duties, and the constitution forbids describing it that way in a README or a briefing.

The real independent review is downstream

The platform team. Always. Everything here is an input to that review, never a substitute for it.

What "approved" means

One developer performed a structured self-check of a defined depth. Not senior security sign-off — unless a qualified senior reviewer actually did it.

Automation has a ceiling

Automated gates reliably catch mechanical issues. They do not reliably catch authorization-logic flaws. The human gate is only as good as the human.

Name which one ran

Never write evidence implying an automated gate ran when a person worked through the checklist by hand. Say which it was.

The uncomfortable overlap, stated on purpose

Offline and air-gapped projects get the weakest enforcement — there's no server to block a bad merge — and the weakest local AI reasoning, while being exactly where a miss costs the most. The conclusion drawn is not "close enough." It's that offline builds need more human rigor, not the same.

10

Two rules that override everything

Sensitive values never enter the AI's view

Real account IDs, server addresses, secrets, credentials — never read, never repeated, never stored. Placeholders everywhere. And the primary control is structural: keep those values somewhere the AI physically cannot see them. Ignore-files are a backup, not the defense.

Model provenance

No AI model whose original weights came from an adversary nation may be used in the engine or embedded in anything it produces — and this binds on where the base model came from, not who uploaded it. A Western repackaging of a Chinese base model is still excluded. This judgment is human-confirmed, because no official approved-model list exists to check against.

Neither can be relaxed by a work instruction. They apply in every session regardless of the task.

Read this before quoting the status above

"Not yet automated" does not mean "not happening." Those checklists run today — by hand, with the same binary verdicts, recorded the same way. The gate is real; the automation is what's pending. That distinction is the whole point of the previous section.

12

Where it's headed

Today the engine runs on a hosted commercial model. The target is a fully offline machine at a forward-deployed unit — no internet at all — running two different local models: one builds, a different one inspects, with a larger model available on an external graphics card where the hardware allows it.

The reason for two different model families isn't redundancy. It's that the bias firewall becomes structural: the reviewer isn't just a second session of the same system, it's a genuinely different one.
