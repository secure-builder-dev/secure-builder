# The four folders

© 2026 Casey Houle. All rights reserved.

Implemented 2026-09-21 (proposed the same day; the proposal is superseded by
this record). Every file the engine owns or produces sits in exactly one of four
folders, and the folder's name says what kind of thing it holds, so a user who has
never read a spec can answer "where do I look?" without help. The four kinds are
the same in both places the engine lives.

| folder | question it answers | mutability |
|---|---|---|
| **rules/** | what is the system required to do? | human-authored; changed only through the governance protocol |
| **harness/** | what does the checking? | engine-owned code; replaced whole on update, never edited in place |
| **records/** | what happened? | append-only; rows are superseded, never edited |
| **work/** | what is in flight right now? | transient; safe to delete, regenerated by the next command |

*Rules are what you promised, harness is what checks it, records are what it
found, work is scratch.* The folder holding the code is named `harness`, not
`engine`, because `.engine/harness/` already existed, the entry point
`python .engine/harness/run.py` was already the one users typed, and
`.engine/engine/` would have read badly.

## In a project (`.engine/`)

```
.engine/
  .gitignore                      the folder's own ignore file (work/, records/scan/raw/)
  rules/      RULES.md, agents/ (reviewer definitions), reference/, config.json,
              control-manifest.json, governance.json, dependency-policy.json,
              license-policy.json, catalogues/, models/     <- the governed set, and nothing else
  harness/    engine/ (the package), selftest/, run.py, reviewers/ (drivers, MODELS.md),
              hooks/, seeds/ (the engine's reference copy of every seeded document,
              in place of the old `.engine-reference` suffix), VERSION, placed.json,
              CHANGES.md, DATA.md
  records/    gate-log.md, findings-register.md, governance-changelog.md,
              mutation-results.md, standing-state-deltas.md, started/,
              coverage-inventory.md, undeclared-controls.md, generated-truth.md,
              reconciliation-obligations.md, carried-findings.md, ingest-records.md,
              high-side-changes.md, currency-verified, scan/ (stamp.json,
              actionable.md, carried.md, detection-data-date, raw/, sbom/)
  work/       handoff-*.md, gate-*-checklist.md, gate-*.json, verdict-*.json,
              raw-*.json, coverage.json, snapshots/, rules-at-base-*/, bakeoff*/
```

The project's own files (`src/`, `tests/`, `plans/`, `tickets/`, `AGENTS.md`)
stay where they are — they are not the engine's. `AGENTS.md` is the one engine
seed outside `.engine/`, because the agent runtime reads it from the root.

**Migration.** `update --project P` moves a project laid out the old way into the
four folders before it places anything: each old path is moved with `git mv`
(history follows it), untracked leftovers under a moved directory are merged,
and every move is printed. An old path whose new path already exists is left
alone and named, never merged silently. Running `update` again moves nothing.

## In the harness repository

```
rules/      specs/, v1.0.md, ledger.tsv, GOVERNANCE-SET.md, AMENDMENTS.md, PROVENANCE.md, prompts/
harness/    engine/, selftest/, reviewers/, integration/, run.py     <- the same shape as a placed .engine/harness/
records/    .build-log.md, receipts/, LIFECYCLE-EXERCISE.md, RELEASE-RECORD.md, REVIEW-READOUT.md,
            STRUCTURE.md (this file), NEXT-PROMPT.md
work/       tools/ (progress, ledger, receipt and their tests), hooks/ (the build's own git hooks),
            drive.sh, budget.txt
LICENSE     stays at the root, where licence detection expects it
.engine/    the harness's own placed configuration and records, laid out like any project's
```

`harness/` in the build tree is the tree that `update` places into a project,
so the one entry point works in both places: `python harness/run.py <command>`
here, `python .engine/harness/run.py <command>` there. `python -m engine` is
gone; the pre-commit hook, CI, `progress.py` and the tool tests all call
`harness/run.py`.

## What did not move, and why

- `LICENSE`: root, by convention.
- Paths written into records before the move (`engine/gate.py` in the ledger's
  impl column, `receipts/...` in its receipt column, `CHECK: engine/...` in
  receipts, `engine/export.py` in dispositioned undeclared-control rows): records
  are not rewritten. `progress.py` resolves a path as written and then at its
  relocated place; the undeclared-controls list carries the dispositions to the
  moved paths as new rows.
- The reviewer drivers stay outside the package (`harness/reviewers/`, not
  `harness/engine/reviewers/`): they import `urllib` for the loopback model
  endpoint, and inside the package the harness's own no-network scan would
  flag them. Tried and reverted during the proposal.

## What the move found

- `harness/run.py` computed the project root as two levels up; in the build
  tree it is one. The root is the directory holding `.engine/`, else the
  parent of `harness/`.
- The harness's own coverage collector had the package prefix `engine`
  hard-coded; it now asks `layout.package_dir`.
- Six checks located the harness tree three different ways (`root/engine`,
  `.engine/harness/engine`, the root itself); they now share `engine/layout.py`.
- `append_record` and the scan data-date writer assumed their directories
  existed.
- The governance set's own list, the harness's own governed-document list and
  `EXP-REDACT`'s location were path-bound; all three updated under GOV-1 in the
  harness's own governance changelog.
