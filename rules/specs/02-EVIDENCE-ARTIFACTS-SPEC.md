## 0. How to read this document

Same conventions as the companion spec: **MUST** / **SHOULD** / **MAY**, each requirement followed
by a rationale that names the failure it was written against.

This document specifies the artifacts the harness *produces* — the durable record of what was
checked, when, by whom, with what result, and what was decided about the results. The companion spec
covers the checks themselves.

### The reframing this document assumes

An earlier generation of this subsystem treated records as **internal discipline**: a log so the
team could see its own trend, a register so findings did not recur. That framing is correct but
incomplete.

The records are also, and primarily, the **assessment evidence** for an authorization decision. In a
controlled environment the question is not "did our process work" but "can you show me." An artifact
that satisfies the first question and fails the second is half-built.

This changes several requirements from *nice* to *mandatory*:

- Schema stability, because an assessor reads a series, not a row.
- Traceability from control to evidence, because that mapping is the assessment.
- Integrity and non-repudiation, because "we could have edited this" is a finding.
- Export and packaging, because evidence that lives only inside a working repository is not
  deliverable.

**Scope boundary and a caution.** This document maps the harness's artifacts onto the *shape* of a
standard authorization package. It does **not** claim assessor acceptance, and it is not a
substitute for an ISSO's judgment about what a specific authorizing official requires. The mapping
in §10 is offered as a starting point to be validated, not a conclusion.

### What these records are, stated before anything else

**The gates that produce most of these records are automated reviewers.** A language model applies a
fixed checklist to a diff in an isolated context and writes a verdict. That is what happened, and
every requirement in this document assumes it is said out loud.

The framing that follows from it is not a weaker claim than the alternative — it is a stronger one:

> These artifacts are **contemporaneous evidence produced by the development process itself**,
> generated by automated review against a versioned checklist, and **attested by a named human**
> who is accountable for the unit of work.

Compare that to the usual position, where evidence is reconstructed after the fact by people
recalling what happened. Evidence generated by the process that did the work is contemporaneous,
which is exactly the property that makes it credible — and contemporaneity is worth more than the
appearance of manual review.

It only works if it is stated first. An assessor who discovers partway through that the assessment
evidence was machine-generated, and that nothing disclosed it, does not simply discount that
evidence; they lose confidence in the whole package, including everything in it that is solid. The
disclosure requirements in §3.1 and §10.5 exist to make the honest version the only version
available.

## 1. Premises specific to evidence

### 1.1 An artifact nobody can read later is not evidence

**Premise.** Records are written by the process that produced them, in the vocabulary of that
process, and read months later by someone who was not present and does not share the vocabulary.

**Consequence.** Every record MUST be interpretable without access to the session that wrote it.
Identifiers MUST resolve. Abbreviations MUST be expanded somewhere the reader will find.

### 1.2 A clean record is a suspicious record

**Premise.** A log showing only passes describes a process that never caught anything. That is
either untrue or an indictment of the process.

**Consequence.** Records MUST capture failures, re-runs, and the path from finding to resolution —
not only terminal states. The intermediate rows are the ones that demonstrate the process works.

### 1.3 A decision without a durable record is not a decision

**Premise.** The specific failure this subsystem exists to prevent: a risk is found, the attack path
is written out, a mitigation is *named* as the thing that would make acceptance safe, the risk is
accepted on that basis — and the mitigation is never built. The acceptance is real; the compensating
control is fictional. Nothing re-surfaces it, because gates are stateless and read only the change
in front of them.

**Consequence.** A risk acceptance MUST carry, in the record itself, the compensating control and
**proof that the control exists**. An acceptance whose compensating control is unbuilt is not an
accepted risk. It is an open risk with paperwork.

### 1.4 Records must survive the tooling that wrote them

**Premise.** The harness will be rewritten. The records must outlive it.

**Consequence.** Records MUST be plain text in a version-controlled, human-readable format. No
database, no proprietary container, no format requiring the harness to read.

### 1.5 The schema is part of the evidence

**Premise.** An assessor reads a *series* of records and looks for consistency. A column that changed
meaning halfway through the series destroys the series, because no row can be trusted to mean what
it appears to mean.

**Consequence.** Record schemas MUST be versioned, MUST be validated mechanically, and MUST NOT be
changed by an edit that leaves earlier rows in the old shape without marking them.

## 2. The record set

Seven artifact classes. Each is specified in its own section below.

| # | Artifact | Written by | Cadence | Append-only |
|---|---|---|---|---|
| 1 | Gate log | Each gate, at completion | Every gate run, including re-runs | Yes |
| 2 | Findings register | Human, or agent transcribing a human decision | On each P0/P1 finding and each risk acceptance | Rows appended; status may change |
| 3 | Governance changelog | The change author | Every change to the rule set | Yes |
| 4 | Scan artifacts | The scan subsystem | Every scan run | Replaced per run; stamped |
| 5 | Standing-state snapshots | The state probe | Every gate, keyed by commit | Yes, per commit |
| 6 | Coverage inventory | The inventory probe | On demand and at close | Regenerated |
| 7 | Generated system truth | The truth generator | At close, and on demand | Regenerated |

**REQ-2.1** All seven MUST live under version control in the project repository, except where §2.2
applies.

**REQ-2.2** Per-clone runtime state (snapshot history keyed by local commits) MAY be excluded from
version control, but the *derived deltas* that a gate acted on MUST NOT be. Rationale: the delta is
the evidence; the raw snapshot is working material.

**REQ-2.3** Scan **raw output** MUST be excluded from version control by default and MUST be
exportable on demand (§6.4). Rationale: it is large, high-churn, and may carry environment
identifiers that do not belong in a repository.

**REQ-2.3.1** The scan **verdict stamp** is a record, not an artifact, and MUST be committed.

**Rationale — resolving a contradiction between two requirements that both read as obviously
correct.** Companion spec 01 REQ-3.3.1 requires the handoff to verify a stamp describing *this exact
commit*, and §10.2.2 requires the scan bundle in the export. If the stamp is excluded from version
control it is local to one machine: a gate run in CI, or on a colleague's checkout, or on the other
side of a domain boundary, cannot see it, and the precondition either fails spuriously or is
disabled. Splitting the two — the stamp travels, the raw output does not — satisfies both
requirements and costs a few hundred bytes per scan.

**REQ-2.3.2** The stamp MUST NOT contain environment identifiers. It carries commit, digests,
verdict, scanner set and timestamp; nothing that names infrastructure.

### 2.4 Concurrency and the single-writer assumption

**REQ-2.4.1** The record format assumes **one unit of work in flight at a time**, and the
implementation MUST state this assumption where an operator will read it.

**Rationale, and why stating it is the requirement.** Every record here is an append-only table in
version control, and every process assumes a single writer. With two developers on two branches:
gate log rows conflict on every merge; the standing-state snapshot diffs against "the previous
gate's snapshot," which is ambiguous across concurrent branches; the coverage inventory races.
Markdown tables are close to the worst possible format for concurrent append.

This is a design constraint, not a defect — it matches how the process actually runs, and building
concurrency machinery before it is needed would add failure modes to buy nothing. What is not
acceptable is leaving it undeclared, because then the first second developer discovers it as a merge
conflict **in the assessment record**, which is the worst possible place to learn about a design
assumption.

**REQ-2.4.2** Where two units of work do run concurrently, conflicts in record files MUST be
resolved by **keeping both rows**. A resolution that drops a row is a record deletion (§12).

**REQ-2.4.3** The documented migration path, for a team that outgrows the assumption, is **one file
per gate run in a directory, assembled into the series on read**. Rows then never conflict, because
two runs never write the same file.

**REQ-2.4.4** An implementation adopting REQ-2.4.3 MUST preserve the ability to read the whole
series as one artifact. The series is what an assessor reads; the storage layout is an
implementation detail and must stay one.

### 2.5 Timestamps

**REQ-2.5.1** Every record's timestamp MUST be recorded in a single stated timezone, and the
implementation MUST state where the time comes from.

**Rationale.** Every artifact here carries a timestamp and none of them is attested. This is cheap
to state and an assessor may ask; "the workstation clock" is an acceptable answer and an unstated
answer is not.

**REQ-2.5.2** Where a record's ordering is load-bearing — the started marker preceding its completed
row (§3.5), status history (§6.3.3) — the ordering MUST also be establishable from version control
history, not from the timestamps alone.

### 2.6 Growth

**REQ-2.6.1** Records that grow without bound MUST have a defined rotation, by period, with an index
that preserves the series as readable.

**Rationale.** A gate log after three years is a table with thousands of rows. Specifying rotation
now costs a paragraph; specifying it later is a migration of the single most important artifact in
the package, performed under time pressure because someone finally could not open the file.

**REQ-2.6.2** Rotation MUST NOT delete. Rotated records move; they do not disappear.

## 3. The gate log

The primary assessment record. If only one artifact survives, this is the one that matters.

### 3.1 Content

**REQ-3.1.1** One row MUST be appended per gate run, **including every re-run**.

**REQ-3.1.2** Each row MUST record at minimum:

| Field | Why an assessor needs it |
|---|---|
| Date | Establishes the assessment occurred, and when relative to the change |
| Unit of work | Ties the assessment to a scope |
| **Range** (base..head) | The exact commits assessed — makes the row re-derivable |
| **Run number** | Distinguishes a first attempt from a third; the series is the evidence |
| Finding count **and identifiers** | Count alone cannot be traced; identifiers can |
| Tickets opened | Shows findings went somewhere |
| Verdict | The result |
| Reviewer identity | Which reviewer ran |
| **Reviewer class** | `human` · `automated` · `automated-with-human-review`. See REQ-3.1.5 |
| **Attested by** | The named human accountable for this unit of work |
| **Harness version** | Which build of the checks produced this verdict |
| **Checklist version** | What the reviewer was asked (companion spec 01, REQ-1.5.1) |

**REQ-3.1.5** Every row MUST record the **reviewer class**, and a row whose class is `automated`
MUST NOT be presented as an independent human assessment anywhere in the record set or the export.

**REQ-3.1.6** Every unit of work MUST carry a **human attestation**: a named person who reviewed the
outcome and is accountable for it.

**Rationale.** An identity string naming an agent does not establish accountability; it names a
process. Accountability requires a person, and the record must say which one. This is also the field
that converts "a machine reviewed this" into "a machine reviewed this and a named engineer stands
behind the result" — which is the claim that is both true and defensible.

**REQ-3.1.7** The attestation MUST be distinguishable from the gate verdict. A human who attests is
not thereby recorded as having performed the review.

**Rationale.** Conflating the two would recreate exactly the misrepresentation these requirements
exist to prevent, in the opposite direction.

**REQ-3.1.8** Where the harness version or checklist version cannot be determined, the row MUST
record that fact rather than omitting the field. Rationale: an empty column reads as *not
applicable*; an explicit *unknown* reads as what it is.

**REQ-3.1.3** The range MUST be recorded as commit identifiers, not branch names. Rationale: a
branch name is not a fixed point; the branch moves or is deleted and the row stops resolving.

**REQ-3.1.4** Finding identifiers MUST be recorded, not only counts.

**Rationale.** "3 findings" cannot be traced to anything. "3: F-21, F-22, F-23" can be followed to
the tickets, to the fixes, and to the re-gate row that shows them closed. The count is a summary;
the identifiers are the evidence.

### 3.2 An epic that took three rounds shows three rows

**REQ-3.2.1** Re-runs MUST append, never replace.

**Rationale, and the requirement most at risk of being "tidied."** An implementer looking at three
rows for one unit of work sees noise and consolidates to the final pass. That deletes the evidence.
The three rows are the demonstration that the gate found things and that they were fixed; a single
passing row is indistinguishable from a gate that never found anything. Per §1.2, the clean version
is the less credible one.

### 3.3 Schema integrity

**REQ-3.3.1** The gate log's column schema MUST be defined in exactly one authoritative place.

**REQ-3.3.2** An automated check MUST assert that the table header in the record file matches the
schema the writing procedures emit.

**Rationale — observed failure.** In the reference, the record template carried a seven-column
header inherited from an earlier generation, while the rules and both gate procedures specified
eight columns with different fields — among them the range and the run number, which the template
had nowhere to put. These are not a superset and a subset; they are different schemas describing
different things. A gate following its instructions would have written rows that did not fit the
table it was writing into, and nothing would have objected. The series would have been unreadable
from the first row.

**REQ-3.3.3** A schema change MUST either migrate existing rows or mark the version boundary
explicitly in the file.

### 3.4 Separation of gate types

**REQ-3.4.1** Where multiple distinct gates run (quality, security), each MAY maintain its own
detailed log, but a single consolidated log MUST exist that an assessor can read as one series.

Rationale: two logs with different schemas and no join key is the same problem as §3.3 in a
different shape.

### 3.5 Run attestation — the record must be contradictable

**REQ-3.5.1** The handoff generator MUST write a **started marker** before a gate runs, recording
the range, the head commit, a timestamp, and the run number.

**REQ-3.5.2** A mechanical check MUST assert that every started marker has a corresponding completed
row, and MUST report any marker that does not.

**REQ-3.5.3** The check MUST run in the ordinary mechanical set, not as a maintenance tool.

**Rationale — this is the most gameable artifact in the package and currently nothing can
contradict it.** The gate log is written by the same agent whose verdict it records. Two failures
follow, and neither requires bad faith — ordinary optimization finds both:

- An agent that fails a gate, fixes, re-runs and appends only the passing row. REQ-3.2.1 requires
  re-runs to append; **nothing detects a re-run that did not append**, because the evidence of the
  omission is the omission.
- A row written with no run behind it.

This document repeatedly insists that a check which cannot fail is worthless. Without a started
marker, the gate log is a record that cannot be contradicted — and it is simultaneously the artifact
this document opens by calling the one that matters most if only one survives.

The started marker is written by a *different* component (the handoff generator, companion spec 01
§3.3) at a *different* time, before any verdict exists to be inconvenient. That asymmetry is the
whole mechanism: a missing failing row becomes a visible, checkable gap rather than an absence of
evidence.

**REQ-3.5.4** A started marker MUST NOT be deletable as part of normal operation. Its removal is a
record deletion and falls under §12's prohibition.

## 4. The findings register

This is the artifact that makes the system learn. It has two tables with different semantics, and
conflating them destroys both.

### 4.1 Table A — Permanent checks

**REQ-4.1.1** Every P0/P1 finding, from **any** source — gate, incident, peer review, external audit
— MUST become a row here **before its fix commits**.

**REQ-4.1.2** Each row MUST record: an identifier, the *class* of finding it catches (not the
instance), the mechanism that now catches it, where that mechanism lives, and its status.

**REQ-4.1.3** The finding class MUST be written generally enough to catch the next instance.

Rationale: "user X could see user Y's records on the reports endpoint" is an instance. "A
record-scoped query missing its ownership filter" is a class. Only the class prevents recurrence.

**REQ-4.1.4** **Table A MUST be read at gate start.** If a row's named mechanism is missing or
broken, that MUST be a blocking finding — the check itself has regressed.

**REQ-4.1.5** The `lives in` pointer MUST resolve. An automated check MUST verify this.

**Rationale — observed failure.** In the reference, six of eleven rows pointed at sections of a file
those sections had been moved out of during a restructure. By the register's own rule (REQ-4.1.4),
the register was in a failing state and no gate had noticed, because nothing verified the pointers.
A findings register whose pointers rot becomes a list of claims about checks that may or may not
exist — which is worse than no register, because it reads as assurance.

### 4.2 Table B — Accepted risks and compensating controls

**REQ-4.2.1** A risk acceptance row MUST record all of:

| Column | Requirement |
|---|---|
| Risk | What could go wrong |
| **Attack path** | Concretely, what an attacker actually does. If this cannot be written, the risk is not understood well enough to accept |
| Compensating control | What makes accepting it safe |
| **Proof it exists** | The named test or check, and evidence it runs. An intention is not proof |
| Re-review trigger | The event that forces reconsideration — a deployment to a shared environment, a new consumer, a release |
| Status | See REQ-4.2.3 |

**REQ-4.2.2** **Table B MUST be read at gate start and at every release decision.** Any row whose
proof column is unsatisfied MUST be reported **every run, without exception**, until it is satisfied.

**REQ-4.2.3** A row may be marked accepted **only** when the proof column is satisfied. Anything else
is open, regardless of how well-reasoned the original decision was.

**Rationale.** This is §1.3 made mechanical. The decision can be entirely defensible and the outcome
still bad, because the record was not durable and the compensating control was never verified.

### 4.3 Who may write

**REQ-4.3.1** Rows MUST be added by a human, or by an agent transcribing an identified human
decision.

**REQ-4.3.2** An automated agent MUST NOT accept its own finding. That is self-approval.

### 4.4 Ungated inbound code

**REQ-4.4.1** Where a change enters the protected branch without passing a gate and the team
knowingly accepts it, that MUST be recorded as a row here rather than left implicit.

Rationale: an unrecorded exception is indistinguishable from an undetected gap.

## 5. The governance changelog

Specified in the companion spec §11.8. Restated here as an evidence artifact because its assessment
value is distinct from its governance value.

**REQ-5.1** One row per change to the rule set, recording: date, change identifier, file and section,
base and resulting commit, external grounding, and human sign-off.

**REQ-5.2** The sign-off field MUST record **what the human was shown**, not merely that approval
occurred.

**Rationale.** A row reading "approved" is unfalsifiable a year later. A row reading "approved after
being shown these two hunks, and the note that this row was written after the commit rather than
before" lets a later reader judge whether the approval covered what actually changed.

**REQ-5.3** Where a row is written after the fact rather than before, it MUST say so.

Rationale: a retroactive record presented as contemporaneous is a worse problem than a retroactive
record that admits it.

**REQ-5.4** Where a change rode along with an authorized change but was not itself authorized, that
MUST be called out in the row so it can be reverted independently.

**REQ-5.5** This artifact is the harness's **configuration change control record**. It SHOULD be
treated as the primary evidence that changes to the assessment criteria were controlled.

## 6. Scan artifacts

### 6.1 What is produced

**REQ-6.1.1** Each scan run MUST produce: raw per-tool output, a routed actionable document, a
carried-findings document, and a verdict stamp.

**REQ-6.1.2** Raw output MUST be retained in its native format. Rationale: a summary cannot be
re-analyzed; raw output can.

### 6.2 The verdict stamp

**REQ-6.2.1** The stamp MUST record at minimum the commit scanned, the verdict, and a timestamp.

**REQ-6.2.2** A stamp naming a commit other than the current head MUST be treated as no stamp.

**REQ-6.2.3** The stamp MUST record which scanners ran, so a partial scan is visible as partial.

### 6.3 Carried findings

**REQ-6.3.1** Findings with no available remediation MUST be recorded in a form directly usable as
a plan-of-action record, with at minimum: identifier, affected component and version, severity, the
reason no fix is available, an **owner**, a **scheduled remediation milestone and date**, a
**review-by date**, and **status history**.

**Rationale.** "Input to a risk-tracking process" leaves a person to assemble the deliverable by
hand — which is precisely the hand-assembly this document exists to eliminate. A plan of action is
not a list of problems; it is a list of problems with dates and owners against them, and the fields
that make it one are all available at the moment the finding is carried. Capturing them later means
reconstructing them.

**REQ-6.3.3** Status history MUST be append-only, so the interval between detection and remediation
is readable from the record.

**REQ-6.3.4** A carried finding whose review-by date has passed, or for which an upstream fix has
since become available, MUST become blocking (companion spec 01, §4.10).

**REQ-6.3.2** A carried finding MUST have an owner and a re-review trigger, per §4.2.

### 6.4 Export and handling

**REQ-6.4.1** Scan artifacts MUST be exportable as a dated bundle.

**REQ-6.4.2** Export MUST be capable of redacting environment identifiers — registry paths, host
names, account identifiers, image digests — so a bundle can cross a boundary the working repository
cannot.

**Rationale.** Raw scanner output routinely embeds infrastructure detail. An evidence bundle is
handed to people and systems that the development environment is not cleared to talk to. Redaction
at export, rather than at scan time, keeps the raw artifact complete for internal analysis while
making the deliverable safe.

**REQ-6.4.3** Vulnerability identifiers, package names and versions are the *content* of the
evidence and MUST NOT be redacted.

## 7. Standing-state snapshots

### 7.1 Content and cadence

**REQ-7.1.1** A snapshot MUST be captured per gate, keyed by commit, recording the fixed measurement
set defined in the companion spec §9.1.2.

**REQ-7.1.2** Re-running at the same commit MUST be idempotent.

### 7.2 The delta is the evidence

**REQ-7.2.1** The **delta** between snapshots, and its disposition, MUST be durable even where raw
snapshots are not.

**REQ-7.2.2** Each delta MUST carry a disposition: a findings-register row explaining why it is
expected, or a ticket.

**REQ-7.2.3** This artifact series is the harness's **continuous monitoring record**. It SHOULD be
presented as such.

## 8. Coverage inventory

### 8.1 Purpose

**REQ-8.1.1** An inventory MUST classify every source file as *assessed by a gate* or *never
assessed*.

**REQ-8.1.2** The signal for assessed MUST be evidence-based and traceable: the file entered the
protected branch via a merge whose identifier appears in the gate log.

**REQ-8.1.3** The inventory MUST NOT present "assessed once" as a clean bill of health.

### 8.2 Assessment meaning

**REQ-8.2.1** This artifact defines the **assessed boundary** of the system: the portion of the
codebase that the assessment record actually covers.

**Rationale, and why this matters more than it first appears.** Most projects adopt a harness partway
through their life. A large part of the codebase predates every gate and has never been read by one.
If the authorization package implies the whole system was assessed, that is a material
misrepresentation. An explicit inventory converts an unbounded unknown into a declared, finite,
burn-down-able scope — which is both more honest and more defensible than silence.

---

## 9. Generated system truth

**REQ-9.1** The harness MUST generate, from the code itself, an inventory of the system's actual
interfaces and data structures.

**REQ-9.2** These artifacts MUST be regenerated, never hand-edited.

**REQ-9.3** A comparison MUST exist between generated truth and the planned design, and each
divergence MUST be a human decision — revise the plan, or open a ticket — never a silent
reconciliation.

**REQ-9.4** Generated truth is the input to the negative-test enumeration in the companion spec
§5.2.4. Its accuracy is therefore load-bearing for a control, not merely documentation.

## 10. Mapping to an authorization package

This section is the reframing. **Validate it with your ISSO before relying on it.**

### 10.1 What the harness already produces

Most of what an assessment needs is already being generated as a by-product of the development
process. Naming the correspondence is most of the work of making it deliverable.

| Harness artifact | Corresponds to | Relevant control families |
|---|---|---|
| Control manifest + wiring verification | Control implementation evidence | Implementation narrative; assessment |
| Mutation results | Developer security testing evidence | Developer testing; development process |
| Gate log | Assessment records | Assessment and authorization |
| Security gate verdicts | Assessment findings | Assessment and authorization |
| Carried findings | Plan-of-action input | Remediation planning |
| Scan artifacts | Vulnerability monitoring evidence | Vulnerability monitoring; malicious code protection; flaw remediation |
| Governance changelog | Configuration change control record | Configuration management |
| Standing-state deltas | Continuous monitoring record | Continuous monitoring |
| Coverage inventory | Assessed-boundary declaration | Component inventory; boundary definition |
| Findings register Table B | Risk acceptance record | Remediation planning; risk assessment |
| Generated truth | Interface and data inventory | Boundary and data flow |
| Composition inventory (SBOM) | Software component inventory | Component inventory; supply chain |
| Artifact binding (commit ↔ digest) | Integrity of the delivered artifact | Software integrity; configuration management |
| Plan-of-action records | Plan of action and milestones | Remediation planning |
| Manifest completeness probe | Declared-vs-actual control coverage | Assessment scope |
| Disclosure statement | Assessment methodology | Assessment and authorization |

**The observation worth drawing out.** This is an evidence pipeline that was built for engineering
discipline and happens to produce, as exhaust, most of an assessment package. That is a stronger
position than the usual one, where evidence is assembled after the fact by people reconstructing
what happened. Evidence generated by the process that did the work is contemporaneous, which is
exactly the property that makes it credible.

### 10.2 What is missing for delivery

**REQ-10.2.1** A **control-to-evidence traceability index** MUST be generated, mapping each declared
control to: its implementation location, its proving test, its mutation result, the gate runs that
assessed it, and any carried findings against it.

**Rationale.** This index *is* the assessment, expressed in the form an assessor reads. Every input
to it already exists in the harness; nothing currently joins them. Without the join, an assessor has
to construct the mapping by hand from several files, and will not credit what they cannot follow.

**REQ-10.2.1a** The index MUST emit in a shape that maps onto a **security requirements traceability
matrix**, and MUST carry each control's implementation status (companion spec 01, REQ-7.2.4) and, for
hybrid controls, the shared-responsibility counterpart.

**Rationale.** The assessment process already has an artifact for exactly this — a per-control
statement of what implements it, who is responsible, and what evidence demonstrates it — and it
already has vocabulary for the inheritance split. Emitting into that shape, with those words, means
an ISSO can drop the output into the package rather than translate it. Inventing a parallel
vocabulary for the same concepts costs nothing to avoid and, left in place, guarantees that every
consumer of this artifact does a manual mapping step that can be got wrong.

**REQ-10.2.1b** The index MUST reproduce the manifest's scope statement (companion spec 01,
REQ-7.2.1a), so that a reader of the index alone cannot mistake it for the complete control set.

**REQ-10.2.2** A **package export** MUST exist producing a dated, self-contained bundle: the
traceability index, the gate log series, the findings register, the governance changelog, the
standing-state deltas, the coverage inventory, the composition inventory for each shipped image
(companion spec 01, §4.9), the plan-of-action records (§6.3), the redacted scan bundle, the
degradation statement (spec 04, §7), and the disclosure statement (§10.5).

**REQ-10.2.3** The export MUST carry a manifest listing every included artifact with a content hash.

**REQ-10.2.4** The export MUST record the commit it describes, so the package and the system state
are bound together.

**REQ-10.2.5** The export MUST support classification marking applied uniformly, and MUST be capable
of refusing to export when marking is required and not configured.

**REQ-10.2.6** An **implementation narrative** generator SHOULD exist, producing per-control prose
from the manifest plus the code. This is the gap between a machine-readable register and the
narrative form an assessment document expects.

**REQ-10.2.7** Gate log rows SHOULD record which control identifiers were assessed in that run, so
traceability runs both directions.

### 10.3 Integrity

**REQ-10.3.1** Records MUST be append-only by convention, and that convention MUST be checkable —
an automated check SHOULD verify that historical rows were not modified.

**Rationale.** Version control provides the history, but a reader must be told to look. A check that
asserts "no previously-committed row was altered" converts an implicit property into a stated one.

**REQ-10.3.2** Where stronger non-repudiation is required, commits carrying record updates SHOULD be
signed.

**REQ-10.3.3** The export manifest's hashes (REQ-10.2.3) provide bundle-level integrity and MUST be
computed at export, not stored.

### 10.4 Retention

**REQ-10.4.1** Records MUST be retained for at least the authorization period plus the retention
requirement applicable to audit records in the relevant baseline.

**REQ-10.4.2** Retention MUST NOT depend on the harness continuing to exist. Plain text in version
control satisfies this; a database does not.

---

### 10.5 Disclosure

**REQ-10.5.1** Every export MUST carry a **disclosure statement** describing how the evidence was
produced: that the gates are automated reviewers applying a versioned checklist, which artifacts are
machine-generated, which are human-authored, and who attested.

**REQ-10.5.2** The statement MUST appear at the front of the bundle, not in an appendix.

**REQ-10.5.3** The statement MUST distinguish the deterministic artifacts — mechanical checks,
control wiring verification, mutation results, composition inventories — from the non-deterministic
ones, the agent reviewers' verdicts (companion spec 01, §1.5).

**Rationale.** This is the difference between a package whose provenance is a strength and one whose
provenance is a discovery. Machine-generated, contemporaneous, checklist-driven evidence with a
named human attestation is a genuinely strong position, and it is only available to a package that
says so up front. Discovered late, the same facts read as something that was being kept quiet, and
the doubt does not stay contained to the artifacts it applies to.

**REQ-10.5.4** The statement MUST be generated from the record set, not hand-maintained. Rationale:
a hand-maintained disclosure drifts from what the harness actually does, and a disclosure that is
wrong is worse than none.

## 11. Failure semantics for records

### 11.1 A missing record is a finding, not a gap

**REQ-11.1.1** Where a record is required and absent, the process MUST report it rather than proceed
silently.

**REQ-11.1.2** A missing record SHOULD open a ticket rather than block, **except** where its absence
would leave another check verifying nothing.

Rationale: an unwritten record leaves nothing inert — it is a bookkeeping failure. Control decay is
the exception, because it silently disarms a running check.

### 11.2 A record that cannot be parsed is missing

**REQ-11.2.1** Records MUST be mechanically validated against their schema on every run.

**REQ-11.2.2** A malformed record MUST be treated as absent, not skipped.

### 11.3 A template is not a record

**REQ-11.3.1** A record file containing only template placeholders MUST be distinguishable from one
containing real entries, and MUST NOT report success.

**Rationale.** This is the companion spec's §7.3.3 applied to records. A freshly seeded register
with no real rows validates successfully — there is nothing to fail. In an assessment context that
is materially worse than an internal false green: it is an empty artifact presented as a populated
one.

### 11.4 Pointers must resolve

**REQ-11.4.1** Every path, section, identifier or ticket reference in a record MUST resolve, and an
automated check MUST verify this.

**Rationale.** See REQ-4.1.5. An audit trail whose references do not resolve is worse than none,
because it consumes the reader's trust before failing.

### 11.5 A verdict can be superseded but never erased

**REQ-11.5.1** Where a verdict is later found to be wrong — a gate passed, the change merged, and a
defect it should have caught is discovered — the original row MUST remain and a **superseding row**
MUST be appended recording: the original row, what was wrong, how it was found, and the disposition.

**REQ-11.5.2** A superseded verdict MUST be visibly marked as such wherever the series is read.

**Rationale.** This case will happen and the document is currently ambiguous about it: §12 forbids
deleting records, and nothing describes how to mark one wrong, which leaves an implementer choosing
between falsifying the record and leaving a known-wrong verdict standing unqualified. Neither is
acceptable and the correct answer — append, mark, never erase — is the same rule the rest of the
document already applies everywhere else.

**REQ-11.5.3** A superseding row MUST produce a finding, dispositioned under the ordinary rule
(companion spec 01, §1.4). A gate that missed something is a defect in the checks.

## 12. Non-requirements

- **No scoring or risk-rating arithmetic.** Severity comes from the source that assigned it. The
  harness does not compute a composite score. Rationale: a composite score is a mechanism for
  presenting known defects as acceptable.
- **No automated risk acceptance.** Ever. See REQ-4.3.2.
- **No record deletion.** Status changes; rows do not disappear.
- **No dashboard as the system of record.** A view MAY exist; the text files are authoritative.
- **No inference of assessment coverage.** A file is assessed because a gate log row says so, not
  because it looks like it was.

## 13. Suggested build order

| Stage | Build | Why here |
|---|---|---|
| 1 | Gate log with the full schema (§3) and its schema check (§3.3.2) | Every other artifact joins to this; a schema fixed later cannot repair the series |
| 2 | Pointer-resolution check (§11.4) | Cheap, and prevents the register rot observed in the reference |
| 3 | Findings register, both tables (§4) | The learning mechanism; valueless retrofitted |
| 4 | Governance changelog (§5) | Adopt as soon as a rule set exists |
| 5 | Scan artifacts and stamp (§6) | Follows the scan subsystem |
| 6 | Standing-state deltas (§7) | Needs the gate log to key against |
| 7 | Coverage inventory (§8) | Needs gate log history to compute |
| 8 | **Traceability index (§10.2.1)** | The highest-value missing piece; all inputs already exist |
| 9 | Package export with manifest (§10.2.2–5) | Makes the rest deliverable |
| 2a | **Run attestation / started marker (§3.5)** | Belongs with stage 1; without it the gate log cannot be contradicted |
| 10 | Implementation narrative generator (§10.2.6) | Last; largest effort, most judgment |
| 11 | Disclosure statement generator (§10.5) | Trivial once the record set exists; do not ship an export without it |

**A note on stage 1.** The schema check is not bureaucracy. The reference implementation ran for
months with a record template whose columns did not match what the gates were instructed to write.
Nothing detected it because nothing compared them. A series with an inconsistent schema cannot be
read as a series, which means the single most valuable artifact would have been unusable at exactly
the moment it was needed.

**A note on stage 8.** The traceability index is the difference between *having* evidence and
*delivering* it. Every input exists today. What is missing is the join — and the join is what an
assessor actually reads.

## Appendix A — Observed drift in the reference implementation

Three defects found in the record set on 2026-09-20. An implementation of this spec should be able
to state why each cannot occur.

| # | Defect | Detected by | Prevented by |
|---|---|---|---|
| 1 | Record template schema (7 columns, prior generation) did not match the schema the gate procedures emit (8 columns, different fields) | Manual comparison | REQ-3.3.2 |
| 2 | Six of eleven findings-register rows cited sections of a file those sections had been moved out of; by the register's own rule the register was failing, and nothing noticed | Manual comparison | REQ-4.1.5, REQ-11.4.1 |
| 3 | A register referenced a companion file that does not exist | Manual comparison | REQ-11.4.1 |

Common signature: **the record and the rule that governs it drifted apart, and nothing compared
them.** Identical in shape to the reviewer-document drift catalogued in the companion spec §6.5.2 —
which suggests the general rule: *wherever a format is defined in one place and written in another,
an automated check must assert they agree.*

## Appendix B — Minimum viable evidence set

If only part of this specification is implemented, this is the subset that produces a defensible
record. Ordered by value per unit of effort.

1. **Gate log with range, run number, and finding identifiers.** Without this there is no assessment
   record at all.
2. **Findings register Table B with an enforced proof column.** Prevents the specific failure in
   §1.3, which is the one that produces findings an outside reviewer rates critical.
3. **Governance changelog with what-was-shown sign-off.** Demonstrates the assessment criteria were
   themselves controlled.
4. **Coverage inventory.** Declares honestly what the record does and does not cover.
5. **Traceability index.** Turns four separate artifacts into an assessment.

Everything else strengthens these five. None of these can be reconstructed after the fact.
